# SRC 正式测试数据链路 P0 修复 + Growth Map 数据真实性修复 — Agent Vibe Coding 完整指令

## 一、任务性质

这是一次 **SRC 正式测试上线前的核心数据链路修复任务**。

目标不是增加新功能，而是修复当前发现的正式测试数据没有可靠写入数据库、Growth Map 可能使用 URL 参数制造“看似正确结果”的问题。

必须优先保证：

> **正式测试显示的数据 = 实际测试数据 = 数据库保存数据 = Growth Map 数据 = Hub 数据 = 重新登录后恢复的数据**

尤其必须彻底保证：

> **testLevel（用户选择测试的等级） ≠ confirmedLevel（根据实际测试结果计算出的确认等级）**

两者必须始终保持业务概念独立。

---

# 二、当前已经确认的问题

## P0-1：登录用户正式测试 API 请求没有携带登录态

当前 `src/app/fulltest/page.tsx` 中正式测试流程使用原生：

```ts
fetch('/api/sessions')
fetch('/api/answers')
fetch('/api/results')
```

而后端需要登录态鉴权。

实际日志已经发现：

```text
POST /api/sessions 401
POST /api/results 401
```

导致：

```text
正式测试
↓
session 创建失败
↓
answers 保存失败
↓
results 保存失败
↓
前端 catch 静默吞掉错误
↓
仍然跳转 result
↓
result 页面依靠 URL 参数显示
↓
Growth Map URL 模式又依靠 URL 参数显示
↓
用户看到“正确结果”
↓
但数据库实际上没有新增正式测试记录
```

这是当前最高优先级问题。

# 三、P0 修复要求：正式测试必须真实写入数据库

## 1. fulltest/page.tsx 使用 authFetch

检查项目当前认证架构，使用现有的 `authFetch`，不要重新设计认证机制。

从现有 `useAuth()` 中取得 `authFetch`。

将正式测试涉及的 API 请求统一改为认证请求。

重点检查：

```text
POST /api/sessions
POST /api/answers
PATCH /api/sessions
POST /api/results
```

全部必须使用项目现有的 `authFetch` 或等价的、能够正确携带当前登录用户 token 的认证请求方法。

不要自行复制 token。

不要新增第二套认证逻辑。

不要修改后端鉴权规则来“绕过”401。

# 四、P0 修复要求：finishTest 必须严格按照成功顺序执行

当前不能出现：

```text
API失败
↓
catch {}
↓
继续跳转 result
```

必须改成可靠的同步流程：

```text
1. 创建 session
↓
2. 确认 session 创建成功
↓
3. 保存全部 answers
↓
4. 确认 answers 保存成功
↓
5. 更新 session 完成状态（如果当前架构需要）
↓
6. 创建 results
↓
7. 确认 results 保存成功
↓
8. 最后才允许 router.push(result)
```

所有关键 API 必须 `await`。

不得后台 fire-and-forget：

```ts
fetch(...).catch(...)
```

尤其不能：

```ts
fetch(...)
router.push(...)
```

# 五、API 失败时必须阻止跳转

如果以下任意一步失败：

* session 创建失败
* answers 保存失败
* session 更新失败
* results 保存失败

必须：

1. 停留在当前页面或显示明确错误状态
2. 告知用户“测试结果保存失败，请重试”
3. 不允许进入一个看起来已经完成的 result 页面
4. 不允许 Growth Map 把未保存的数据当成正式测试结果
5. 控制台保留真实错误信息，方便开发调试

禁止：

```ts
catch {}
```

或者：

```ts
catch {
   router.push(...)
}
```

# 十三、P2：修复 RJB 数据估算口径

当前发现：

RJB500：

```text
实际去重字数 = 499
```

SRC500 与 RJB500 的交集：

```text
323
```

当前 URL 模式可能使用：

```text
499 × SRC mastery rate
```

例如：

```text
499 × 90% ≈ 449
```

这会造成家长误解：

> 好像孩子实际测试了499个人教版汉字。

这是错误的。

---

## 正确原则

RJB 是：

> 教材识字参照

不是 SRC 的正式测试题库。

如果本次正式测试实际只抽测了 SRC500 的部分字，则不能声称：

```text
449 / 499
```

除非这 499 个 RJB 字确实被实际测试。

---

# 十四、RJB显示规则必须重新确认

当前 SRC500：

```text
RJB500 = 499字
SRC500 ∩ RJB500 = 323字
```

如果测试 SRC500：

```text
25% × 323 ≈ 81
```

那么本次实际覆盖 RJB 字大约是：

```text
81
```

因此不能显示：

```text
450/499
```

除非系统真的对499个RJB字进行了独立测试。

# 十五、请严格区分三种数据

## ① RJB教材参照总量

表示：

> 本次SRC500正式测试实际抽测到的RJB交集汉字数量。
