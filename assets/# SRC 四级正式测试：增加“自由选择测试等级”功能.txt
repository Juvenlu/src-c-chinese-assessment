# SRC 四级正式测试：增加“自由选择测试等级”功能

## Vibe Coding 完整开发指令

### 一、开发目标

在现有 SRC100 / SRC300 / SRC500 / SRC800 四级正式测试架构基础上，增加：

> **“推荐测试 + 自由选择任意 SRC 等级测试”**

功能。

当前系统已经可以根据 Quick Assessment / 正式测试结果计算：

* estimatedLevel
* confirmedLevel
* currentLevel
* recommendedTestLevel

目前“开始正式测试”主要进入系统推荐的等级。

现在需要增加一个正式产品功能：

> **登录后的用户，可以按照自己的意愿，在 SRC100 / SRC300 / SRC500 / SRC800 四个等级中自由选择任意一个等级进行正式测试。**

这个功能不仅用于人工 E2E 测试，也是正式产品功能。

---

# 二、最重要的产品原则

必须严格区分以下 5 个概念：

### 1. currentLevel

孩子当前中文等级。

来源：

```text
confirmedLevel ?? estimatedLevel
```

不能因为用户选择了某个测试等级而改变。

---

### 2. recommendedTestLevel

系统根据孩子当前数据推荐的下一步测试等级。

例如：

```text
Mia 当前等级：SRC300
推荐测试：SRC300
```

这是系统推荐，不是用户唯一可以测试的等级。

---

### 3. testLevel

本次用户实际选择进行测试的等级。

例如：

```text
currentLevel = SRC300
recommendedTestLevel = SRC300
testLevel = SRC100
```

完全合法。

也可以：

```text
currentLevel = SRC300
recommendedTestLevel = SRC300
testLevel = SRC500
```

也完全合法。

---

### 4. confirmedLevel

正式测试后，根据正式测试结果和既定 LevelService 规则计算出的确认等级。

必须由正式测试结果决定。

**不能直接等于 testLevel。**

例如：

```text
testLevel = SRC500
```

不代表：

```text
confirmedLevel = SRC500
```

必须根据实际测试结果判断。

---

### 5. test_mode

本功能选择的四级测试仍然属于：

```text
test_mode = 'formal'
```

不能因为用户自由选择等级而改成 sampling。

---

# 三、核心业务规则

## 规则 1：四个等级都允许自由选择

登录用户可以选择：

```text
SRC100
SRC300
SRC500
SRC800
```

任何一个等级。

不应因为当前等级较低而禁止选择更高等级。

例如：

```text
当前 SRC100
可以测试 SRC100
可以测试 SRC300
可以测试 SRC500
可以测试 SRC800
```

同样：

```text
当前 SRC800
可以测试 SRC100
可以测试 SRC300
可以测试 SRC500
可以测试 SRC800
```

---

# 四、自由测试不能改变当前等级

这是本次开发最重要的保护条件。

例如：

```text
Mia 当前等级 = SRC300
```

Mia 主动选择：

```text
SRC100
```

完成测试后，即使 SRC100 测试结果很好，也不能简单地：

```text
currentLevel = SRC100
```

因为：

> testLevel 是“本次测试等级”，currentLevel 是“孩子当前能力等级”。

两者必须完全分离。

---

# 五、自由测试更高等级也不能直接升级

例如：

```text
currentLevel = SRC300
testLevel = SRC800
```

即使进入了 SRC800 测试，也不能直接：

```text
confirmedLevel = SRC800
```

必须继续使用现有正式测试结果计算逻辑：

```text
answers
→ mastery rate
→ stable_char_count
→ stable_vocab_count
→ LevelService
→ confirmedLevel
```

不能为了实现自由测试而修改现有 confirmedLevel 算法。

# 十一、必须增加服务端等级校验

不能只依赖前端 URL。

例如用户手动输入：

```text
/fulltest?level=SRC500
```

后端必须验证：

```text
level ∈ ['SRC100','SRC300','SRC500','SRC800']
```

合法则继续。

非法值：

```text
SRC999
ABC
undefined
null
```

必须安全处理。

不要让非法 level 导致：

* 崩溃
* 错误查询
* 默认错误等级
* 数据污染

---

# 十二、正式测试 session 必须保存 testLevel

这是本次开发的关键数据结构要求。

创建正式测试 session 时，必须明确保存：

```text
test_mode = 'formal'
level = testLevel
```

例如 Mia 当前 SRC300，但主动选择 SRC100：

```text
test_mode = 'formal'
level = 'SRC100'
```

不能保存成：

```text
level = currentLevel
```

也不能保存成：

```text
level = recommendedTestLevel
```

必须是：

> **用户实际选择的 testLevel**

---

# 十三、Answers 必须属于本次 testLevel

例如：

```text
session.level = SRC500
```

那么该 session 中：

* 单字题来自 SRC500
* 词组题来自 SRC500
* answers 属于 SRC500 formal test

不能混入：

```text
SRC300
SRC800
```

题目。

---

# 十四、Results 必须使用 session.level

Results 计算时：

```text
session.level
```

才是本次测试等级。

不要使用：

```text
currentLevel
recommendedTestLevel
estimatedLevel
```

代替。

例如：

```text
currentLevel = SRC300
testLevel = SRC500
```

Results 必须按照：

```text
SRC500 LEVEL_CONFIG
```

计算：

* stable_char_count
* stable_vocab_count
* mastery rate
* 教材覆盖
* 相关指标

---

# 十五、Growth Map 必须正确区分测试等级与当前等级

Growth Map 中应该能够区分：

```text
currentLevel
```

和：


例如：


不要因为 Mia 测了 SRC500 就直接显示：

除非现有 LevelService 根据正式测试结果确实判定她已经达到 SRC500。

# 十七、重复测试规则

允许用户重复测试同一个 SRC 等级。


可以测试多次。

但是需要确认现有 Results / Growth Map 逻辑：

* 是取最新一次？
* 是取最高可信结果？
* 还是按照既有规则合并？

**本次不要擅自改变现有规则。**

如果目前系统已经定义了“最新 formal result”作为确认依据，则继续使用现有规则。

只需要确保：

```text
testLevel
```

被正确保存。
