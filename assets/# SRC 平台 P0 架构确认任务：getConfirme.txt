### 一、任务背景

上一轮 SRC500 API 回归测试已经确认：

* `POST /api/sessions` → 201 ✅
* `POST /api/answers` → 200 ✅
* `PATCH /api/sessions` → 200 ✅

* `selected_answer` 列名问题已经修复
* PATCH session 的 `id` 参数问题已经修复
* authFetch 全链路正常

但是第二轮诊断报告发现了一个潜在的 **P0 架构问题**：

> `confirmedLevel` 可能直接使用正式测试的 `testLevel`，而不是根据 `stable_char_count → numToLevel()` 计算。

然而，当前诊断报告自身存在一个重要矛盾：

一处报告声称当前代码是：

```ts
export function getConfirmedLevel(
  latestFormal: { level: string } | null | undefined
): Level | null {
  if (!latestFormal) return null;
  if (isValidLevel(latestFormal.level)) return latestFormal.level;
  return null;
}
```

但另一处报告又声称当前代码已经是：

```ts
export function getConfirmedLevel(result?: any): Level | null {
  if (!result || !result.stable_char_count) return null;
  return numToLevel(result.stable_char_count);
}
```

这两个结论互相矛盾。

因此：

# 本轮唯一任务

**准确确定当前项目实际生效的 `getConfirmedLevel()` 定义、调用路径以及 confirmedLevel 的真实计算逻辑。**
